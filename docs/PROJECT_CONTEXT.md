# game_kari Project Context

## 1. Project overview

Unityで制作中の戦闘特化型RPG。マップ探索は作らず、以下のループを基本にする。

```text
拠点 → クエスト選択 → 会話イベント → 複数戦闘 → リザルト → 拠点
```

主軸は、戦闘UIと4vs4の陣形型コマンドバトル。

## 2. Repository / local workflow

Repository:

```text
https://github.com/Kenu4000/game_kari
```

Unityで開く本体フォルダは、GitHubからcloneした `game_kari` フォルダに統一する。

CodexやChatGPTで作った変更がGitHubに入ったら、PC側ではGitHub Desktopで以下を実行する。

```text
Fetch origin → Pull origin
```

## 3. Unity / display policy

- Unity使用
- マウス操作のみ
- コントローラー操作は想定しない
- 基準解像度は1920x1080
- 最初は16:9固定
- UIはuGUI + TextMeshPro想定
- Canvas Scalerは `Scale With Screen Size`
- Reference Resolution は `1920 x 1080`
- 日本語フォント問題回避のため、当面は自動生成UIのテキストを英語仮表示にする
- 後で日本語TextMeshProフォント対応を行う

## 5. Battle system overview

- 4vs4のコマンドバトル
- 敵味方それぞれ2×2マス
- 味方には控えキャラあり
- 味方キャラ総数は6人程度を想定
- 行動順はターン開始時に盤面上の敵味方を素早さ順に並べる
- そのターン中に素早さが変わっても順番は変えない
- 次ターン開始時に再計算する
- 交代や回転は行動権を消費しない
- 技またはアイテムを確定するまで、交代や回転を行える

## 6. Grid coordinates

2×2盤面は以下で管理する。

```text
[ FrontTop    ][ BackTop    ]
[ FrontBottom ][ BackBottom ]
```

- Front = 前列
- Back = 後列
- Top = 上段
- Bottom = 下段
- 左が前、右が後ろ

## 7. Mouse control policy

- 左クリック：選択 / 決定
- ホバー：説明表示 / 技の対象マスプレビュー
- 右クリック：親メニューに戻る
- 空いている盤面をクリックしても何も起きない
- 味方や敵にホバーしても何も起きない
- 回転ボタンは味方盤面の近くに常設
- 将来的にマウスホイールで盤面回転する案も検討する
- マウスホイール回転では、勢いよく回した際に360度回ってからブレーキがかかるような演出を検討する

## 8. Command UI

コマンドUIは上部中央に配置する方針。

状態ごとの表示は以下。

```text
通常時：戦う / 交代 / アイテム
戦う選択時：技1〜4
交代選択時：控え一覧
アイテム選択時：アイテム一覧
```

英語仮表示では以下を使う。

```text
Fight / Swap / Item
Skill 1 / Skill 2 / Skill 3 / Skill 4
```

## 9. Skill policy

- 各キャラは技を4つ持つ
- 技は拠点で複数候補から4つを選んで装備する。ポケモンの技選択に近い運用
- 技はストーリー、イベント、レベルアップなどで増える想定
- 技にホバーすると説明表示
- 同時に攻撃対象マスをハイライト
- 対象マスは現在操作中キャラの位置基準でリアルタイムに決まる
- 交代や回転で位置が変わると、対象プレビューも更新
- 技をクリックすると使用確定し、そのキャラの行動終了
- 技選択中に、その技を使うとMPがどれくらい減るかをUI上でプレビューする
- MP0でも使える基本技は初期方針として必須にはしない
- MP0時はパスしかできない状態になってもよいが、バランス調整対象とする

## 10. MP / resource policy

- アイテムとしてHP回復やバフは存在してもよい
- MP回復は非常にシビアにする、または無しにする
- MPの枯渇により、強いキャラだけで戦い続けることを難しくする
- 全員で戦う必要があるバランスを目指す
- レベル差で使われにくいキャラが出る可能性は認識し、調整対象とする
- 弱いキャラでも、盾役、配置役、合体技条件、特定キャラとの連携で出番を作る
- HPも火力も低いが、前衛のMPを少し回復できるような支援キャラは候補に入れる
- MP回復役は強くしすぎるとMP制限の意味が薄れるため、回復量・対象・位置条件を厳しくする
- MP0でも、回転・交代・アイテム使用・合体技条件としての配置役は可能

## 11. Combo skill policy

- 合体技を導入予定
- 初期実装では通常技を優先し、合体技は後から追加する
- 合体技は通常技と同じく、キャラの技枠4つのうち1つとして選択できる想定
- 例：キャラクターAの技3は、自身とキャラクターBが前衛にいることを条件に使用可能
- 合体技の条件には、特定キャラの存在、前衛配置、特定マス、特定バフなどを将来設定できるようにしたい
- 合体技は戦略性を上げる要素であり、見た目の派手な演出にも使う
- 弱いキャラにも、合体技の相方として出番を作れる
- 条件がはまれば合体技を連発できて気持ちよい戦闘を目指す
- 大味化は、条件・MP消費・対象範囲・演出・敵の対策で抑える
- 合体技はキャラ同士の関係性や会話イベントと結びつける
- 合体技の解放は、装備報酬の代わりになる成長報酬として扱う
- 合体技が撃てる陣形になった瞬間、該当キャラの立ち絵を軽く発光させるなどして通知する

## 12. Formation / rotation policy

- 前後列を直接入れ替える専用コマンドは実装しない
- 前衛・後衛の調整は、位置固定のキャラクター交代と盤面全体の90度回転を組み合わせて行う
- 列入れ替えを別コマンド化せず、回転と交代を使ったパズル要素として扱う
- 狙った2人を前衛に並べたい場合、その2人が隣接していればよい
- 縦・横に関わらず、隣接している2人は90度、180度、270度回転によって前線に並べられる
- 回転後、現在操作中キャラの位置と技対象プレビューを更新

## 13. Battle UI layout policy

現行方針では、下部の独立した行動順バーを廃止し、敵味方statusに行動順数字を統合する。

画面構成:

```text
左：EnemyStatusPanel
中央左：EnemyGridPanel
中央右：AllyGridPanel
右：AllyStatusPanel
上中央：CommandPanel
上部/敵側付近：BossNamePlate
味方盤面付近：RotateButton
```

廃止予定:

```text
TurnOrderBar
```

バトルログは廃止。

## 14. Status UI policy

### EnemyStatusPanel

- 画面左側に配置
- AllyStatusPanelの左右反転に近い構造
- 敵種別アイコン
- HPのみ表示。敵MPは表示しない
- 小HPバー
- 行動順数字
- 現在行動中の青枠
- バフ/デバフアイコン欄
- 名前は必要なら小さく表示

### AllyStatusPanel

- 画面右側に配置
- 顔アイコン
- HP/MPバーと数値
- 行動順数字
- 現在行動中の青枠
- バフ/デバフアイコン欄
- キャラ名は基本的に出さない方針

### Status order

- グリッドを移動・回転させてもstatusの並び順は変化しない
- status欄はキャラ/敵個体の固定情報、盤面は現在位置として分ける
- 画面変化を減らして視線移動を抑える

## 15. Turn order display policy

行動順は各statusアイコン横の数字で表示する。

- 数字はターントップから数えた順番
- 各キャラのコマンドが進んでも、ターン中なら数字は変化しない
- 行動前：数字あり
- 行動済み：数字なし、少し暗く
- 死亡：×、グレーアウト
- 未配置：空欄

現在行動中の強調:

- 盤面上の立ち絵を青発光
- 対応するstatus枠も青枠
- 行動順数字1の表示も強調

## 16. Quest interval / reward policy

- クエストは複数戦闘で構成される
- 各戦闘の間に、休憩・死体漁りの2つの選択肢を出す想定
- 会話イベントは独立した選択肢ではなく、休憩または死体漁りに付随するイベントとして扱う
- 条件を満たした場合、休憩・死体漁りのアイコン右上などに会話イベント発生マークを表示する
- 会話マーク付きの選択肢を選ぶと、通常効果に加えて会話イベントが発生する
- 会話イベントは、キャラ関係性の進行や合体技解放につながる可能性がある
- 装備などの物理的な報酬は少なめにする想定
- 技の解放・技候補の増加・会話イベントを主要報酬にしたい
- 仲の良いキャラ同士が合体技を撃てるようになる流れを、戦闘面と物語面の両方の報酬にする

## 17. Character performance policy

- 全キャラを同じ強さにはしない
- あえて性能差をつける
- 例：子供キャラはステータスが低いが、周囲と仲が良いため合体技が多く使える
- 弱いキャラでも、合体技条件・盾役・配置役・関係性イベントによって出番を作る

## 18. Swap policy

- 現在操作中キャラと控えキャラを交代する
- 控えをクリックすると即交代
- 交代は行動権を消費しない
- 交代後も技またはアイテムを使うまで行動終了しない
- 右クリックで交代前には戻さない
- 元に戻したい場合は、交代コマンドで元キャラを選び直す

## 19. Item policy

- 回復アイテムのみ
- 対象は操作キャラの前のマスにいる味方1人
- BackTopのキャラはFrontTopの味方に使用可能
- BackBottomのキャラはFrontBottomの味方に使用可能
- FrontTop / FrontBottomのキャラは前方マスがないため、そのままではアイテム使用不可
- アイテムを使用したら、そのキャラの行動終了

## 20. Acting / animation policy

行動確定後または敵行動中は、コマンドUIを操作不能にする。

画面上部中央に表示:

```text
1行目：使用技名
2行目：使用者名
```

演出方針:

- 攻撃元マスと対象マスを強調表示
- 無関係キャラは少し目立たなくする
- 攻撃時は使用者が少し前に出る
- 被弾時は対象キャラが小さく揺れる
- 各キャラはマス中央下を基準に立つ
- 頭や武器はマス外にはみ出してよい
- 足元はマス内に残す
- 描画順は下のマスほど前面
- 待機モーションは軽い上下揺れ、髪揺れ程度
- 操作中キャラは立ち絵を光らせる

## 21. KO / reserve fill policy

- 空マスは薄いグリッドだけ残す
- 戦闘不能時は爆発して消える
- 味方が戦闘不能になった場合、控え一覧の上から順に自動補充
- 補充位置は倒れたキャラのマス
- 補充時は横からスライドイン

## 22. Buff / debuff policy

初期実装:

- 攻撃アップ
- 防御アップ
- 攻撃ダウン
- 防御ダウン

実装しない:

- 素早さアップ
- 素早さダウン
- 状態異常

ルール:

- 基本持続は2ターン
- 同じ効果は上書き
- 重複加算しない
- 同種の逆効果がかかった場合は打ち消して0に戻す

例:

```text
攻撃アップ中に攻撃ダウン → 0に戻る
攻撃ダウン中に攻撃アップ → 0に戻る
```

## 23. Codex usage policy

Codexは制限があるため、通常相談には使わない。設計・判断・GitHub操作・Unity操作確認はChatGPT側で行う。

Codexを使うのは以下のみ。

- 複数ファイルのコード修正
- Unity C#スクリプト作成
- Editor拡張修正
- コンパイルエラー修正
- PR作成

Codexに依頼する時は必ず以下を指定する。

```text
目的：
対象ファイル：
変更禁止ファイル：
実装内容：
テスト：
出力：
```

Codex環境確認は、`remote` や `origin/main` の有無だけで判定しない。Codex Cloudでは `work` ブランチだけに見えることがあるため、以下を確認する。

```text
pwd
ls
find . -maxdepth 3 -type f | head -50
test -f Assets/Editor/BattleUICreator.cs && echo FOUND_BattleUICreator || echo MISSING_BattleUICreator
test -f docs/PROJECT_CONTEXT.md && echo FOUND_CONTEXT || echo MISSING_CONTEXT
```

OK判定:

```text
FOUND_BattleUICreator
FOUND_CONTEXT
Assets/
docs/
```

PR確認条件:

```text
Can automatically merge
Files changed が想定通り
古いブランチ由来の余計な差分がない
```

Codexがpushできない場合:

```text
変更後ファイル全文を出力してもらい、手元で置き換える
```

ブランチ名は短くする。

```text
codex/ui-layout
codex/fix-font
codex/battle-core
codex/turn-order
codex/combo-skill
codex/context-doc
```

作業が終わった古いCodexブランチは削除する。

## 24. PROJECT_CONTEXT.md update policy

このチャットでは、重要な仕様決定・作業方針変更・トラブル対応方針が固まった場合、確認なしで `docs/PROJECT_CONTEXT.md` へ追記してよい。

ただし、追記の成功・失敗に関わらず、次の応答時に「PROJECT_CONTEXT.mdへ追記したか」「成功したか失敗したか」を伝える。

追記対象の例:

- 戦闘仕様の確定・変更
- UI仕様の確定・変更
- GitHub / Unity / Codexの運用ルール変更
- 作業ログとして残す価値がある失敗と対処
- 新規チャット移行に必要な前提情報

GitHubへの書き込みに失敗した場合は、代わりに追記案を本文で提示し、手元反映できる形にする。
